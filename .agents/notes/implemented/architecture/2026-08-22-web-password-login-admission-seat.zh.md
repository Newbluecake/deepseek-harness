# Agent Note：以一个准入席位保护整个 Web 界面的口令登录

Status: implemented

[English](2026-08-22-web-password-login-admission-seat.md) | 中文

## 问题

Web GUI 只能从回环访问，而且这是刻意的：`dsh web --host 0.0.0.0` 会被直接拒绝，因为该界面能够驱动运行 shell 命令的 agent，开放绑定就等于把远程代码执行暴露给网络。这使得确实想从另一台机器访问自己 harness 的操作员没有任何受支持的办法，只能使用 SSH 隧道，或直接从源码删掉这道拒绝。

看似显然的修法有两处错误。只放宽绑定拒绝会发布一个未认证的 agent；只在 `/api` route 上加登录检查，则仍会向匿名访客提供 SPA、插件 bundle 与 HMR 流，并且以后新增的下一条 route 默认仍无保护。这恰好重新引入了 [`/api` 浏览器信任边界](2026-07-28-api-browser-trust-boundary.zh.md)已经拒绝过的逐 route 追赶式 guard。

其下还有第二个问题。`trustedHosts` 与 `--trusted-host` 看起来像访问控制，实际不是：它们是 DNS 重绑定栅栏，只回答“这个 Host 是不是我们服务的”，从不回答“谁在调用”。因此，即使某个权威已声明受信，特权方法集合——完整的 settings、credentials 与 preset 配置面——仍被钉在回环。即使绑定被打开，远程操作员依然无法访问自己的配置面。

## 决策

给 webserver 增加一个准入席位，并由一个插件占据它。

- **席位（dsh-host-webserver，`registerGate`）**：单一所有者的注册点，在 route 匹配、fallback 和每次 upgrade 之前被征询。只有 webserver 同时看得到这三者，因此覆盖整站的准入决策只能在此真正强制执行。`http` 分支返回 `false` 表示它已作答并接管响应；`upgrade` 分支只做判定，拒绝即销毁 socket——客户端请求切换协议后没有响应可写。gate 抛错时像任何 handler 失败一样被兜住并拒绝请求：策略损坏时是关闭而非放行。在回环绑定上，席位无人占据时一切请求照常提供，因此默认组合保持不变；而在 `0.0.0.0` 绑定上，席位无人占据时改为以 503 拒绝一切请求并销毁每一次 upgrade——一台没有准入所有者却已发布的服务器，等于把远程代码执行直接交给网络。席位逐请求重新读取，因此占据它会打开该服务器，销毁该注册又会重新关闭它。

- **Gate（dsh-host-web-auth）**：一个经 credentials seam 解析的共享口令（`passwordRef`，默认 `DSH_WEB_PASSWORD`），以常数时间比较，并按客户端地址限流。成功后签发一个不透明的进程内会话，以 `HttpOnly; SameSite=Strict` Cookie 返回，并根据 `X-Forwarded-Proto` 添加 `Secure`。口令未配置时拒绝一切请求，因此挂载该行绝不会意外地公开服务。浏览器导航收到本包直接输出的自包含登录页——不能使用 SPA route，因为“未认证者什么也看不到”意味着根本不向匿名访客提供 dist；其余请求收到纯文本 `401`，因为把 HTML 塞进 `fetch` 只会破坏调用方原本期待的内容。

- **会话满足 Host 栅栏。** `isTrustedApiRequest` 增加 `authenticated` 参数：携带存活会话的请求无需声明 `trustedHosts` 权威即可通过 Host 检查。这不是妥协，而是由一个具体性质保证的：会话 Cookie 与源绑定。DNS 重绑定页面抵达我们的 socket 时携带 `Host: evil.example`，浏览器只会发送 evil.example 的 Cookie，永远拿不出我们的。因此，出示会话本身即证明请求未被重绑定——这正是引入 `trustedHosts` 所要建立的性质。跨站与 `Origin` 比对完全不变且仍然适用，因为会话只说明哪个 host 是我们的，从不说明这个 fetch 是谁发起的。

- **已认证调用方默认可以访问特权面**（`allowAuthenticatedPrivilegedMethods`）。证明持有部署口令，与坐在回环控制台前的操作员拥有同一权限；不让他们访问配置面并不能保护什么，只会让远程操作失去用途。希望配置面保持在物理本机的部署可将其设为 false，而在没有认证行时，无论该开关如何，回环钉死都依然成立。

- **绑定拒绝变为组合权限**（`web-startup` 行的 `allowNonLoopbackHost`，默认 false）。CLI 解析阶段看不到认证行是否已经挂载，因此该权限必须显式声明，不能推断。随附 Web bundle 保持 false，并以 disabled 状态随附 `web-auth`：回环仍是默认姿态，操作员通过同时启用二者来选择远程访问。由于该标志只是一项声明而非证明，webserver 在真正可观测之处——分发时、针对存活的席位——强制执行同一项要求，因此设置了标志却忘记挂载行，得到的是一台拒绝服务的服务器，而不是一台敞开的服务器。

- **登录后的跳转目标是解析出来的，不是前缀判断的。** `next` 会经 WHATWG URL 解析器针对一个固定的私有基址解析，并且必须落在该 origin 上——因为浏览器与前缀判断并不一致：`/\evil.com` 与被制表符切开的 `/<tab>/evil.com` 都以单个 `/` 开头，却仍解析到站外。吐出的值要重新检查，因为 `/..//evil.com` 会归一化成 `//evil.com`，那又是协议相对的。

TLS 仍不在范围内：请在反向代理或隧道处终止。按这里唯一的用法读取 `X-Forwarded-Proto` 是安全的，因为伪造值只能添加 `Secure` 属性，而触发它只会损害伪造者自己。

## 考虑过的替代方案

- **按用户建立账号。** 本次拒绝：用户存储、按用户轮换凭据以及会话日志里的 actor 概念都是真正的产品表面，而“允许我自己的操作员从另一台机器进入”并不需要这些。共享口令坦诚地代表一个匿名主体，README 也明确说明了这一点。
- **URL 中的预共享 token。** 拒绝：链接里的 token 会经由历史记录、referrer 与旁观泄漏，而且无法只吊销一个持有者而不为所有人轮换。
- **只 gate `/api`。** 拒绝：它让 SPA、bundle 与 HMR 流保持匿名，并重新建立被浏览器信任边界决策移除的逐 route guard 列表。
- **登录之外还要求 `--trusted-host`。** 拒绝：这只增加流程而没有收益。Cookie 与源绑定已经更直接地建立了它所要证明的重绑定性质；同时要求二者会迫使每个已认证部署维护一张不需要的列表。
- **内置 TLS。** 拒绝：证书获取与续期是已有成熟工具的部署职责；在这里复制它们，效果不如这类部署本来就会运行的代理。

## 后果

- 未来任何 route、fallback 或 upgrade 都天然被准入或拒绝，不再有可能遗忘的逐 route 认证决策。
- loopback 之外的部署启用 `web-auth`、设置 `allowNonLoopbackHost`，无需任何 `trustedHosts` 条目。回环部署完全不变：没有 gate、没有登录提示、没有新增配置。
- 这一对开关中只配了一半会立刻显形：已发布但没有准入行的绑定会处处以 503 作答，而不是照常提供 SPA——这是一次响亮的失败，而非一次无声的暴露。
- 会话不跨重启存活，因此升级或崩溃后每个浏览器都要重新登录。对于由操作员修改配置来轮换的进程内密钥，这是刻意选择。
- 特权方法不再无条件钉在回环，而是取决于是否缺少认证。[`/api` 浏览器信任边界 Note](2026-07-28-api-browser-trust-boundary.zh.md)仍然拥有媒体类型栅栏、重绑定分析以及对逐 RPC guard 的拒绝；这里只修订了其“认证延期”与“回环钉死无条件成立”的表述。
- 如果前方没有 TLS，口令与会话 Cookie 会以明文穿越网络。README 直接说明这一点，而不假装 Cookie 属性已经足够。
